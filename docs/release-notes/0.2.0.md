# Vade v0.2.0 release notes

v0.2.0 is not released yet. These notes describe main as it stands now.
Work that is not merged yet is under [In progress](#in-progress). The
[changelog](../../CHANGELOG.md) has the detailed list of changes.

## In short

- Two Sparks are much faster than in v0.1.0. One chat writes code at 100
  tokens per second, against 65 in v0.1.0.
- Long prompts give their first token sooner on two Sparks. A cold 8K
  prompt takes 2.19 s, against 2.79 s in v0.1.0.
- Two Sparks run 16 short chats together at a 131,072-token context,
  where main `54392da` ran 2.
- One Spark serves a 131,072-token context and a 262,144-token context.
  Two Sparks serve 262,144.
- The prefix cache works on two Sparks. A second question on a 32K-token
  chat answers in under a second. The cache is still off by default.
- A new guide covers the OpenAI-compatible API.
- The agent reads text-based PDF files in your project.
- In direct and agent mode, the agent reads your project instructions,
  such as `AGENTS.md` or `CLAUDE.md`.
- `vade pull` downloads a model from Hugging Face and checks every file.
- A long chat rolls over at the end of the context window instead of
  stopping: the model writes a summary of the older turns.
- `min_p` sampling works on every request surface.
- The answers do not change. FP4-Local gives the same token IDs on one, two
  and four Sparks.

## Where the numbers come from

Each number on this page names its source:

- **The v0.1.0 cards** are the release cards of 2026-10-24 at `5a22651`.
  Their receipts are in the repository:
  [bench/receipts/2026-10-24](../../bench/receipts/2026-10-24/README.md).
- **The end-of-day cards** are the RigMark cards of 2026-10-28 at main
  `76977df`. The
  [benchmarks page](../benchmarks.md#current-2026-10-28-end-of-day-main-76977df-home-dgx-sparks)
  gives their settings and result folders.
- **The confirm run** compared main `285fa8a` with the main before it,
  `54392da`, on 2026-10-28
  ([confirm run](../benchmarks.md#confirm-run-main-285fa8a)).
- **The capacity test** ran on 2026-10-28, and **the context tests** ran
  on 2026-10-28 and 2026-10-29. Their records are not in the repository
  yet. The [benchmarks page](../benchmarks.md#context-windows-main-285fa8a)
  gives their settings and run names.

All cards used the FP4-Local checkpoint unless a line says FP8, greedy
decoding and thinking off. Rates are completion tokens per second, with
drafting ON, the default, unless a line says otherwise. Each card sends its
cold 8K prompt with drafting OFF (`"draft": "plain"`), also in the cards
with drafting ON. So every first-token time after a cold 8K prompt on this
page was measured with drafting OFF.

## Faster answers

**Two Sparks now share every token.** In v0.1.0, two Sparks ran a layer
pipeline: each Spark held half of the layers, so only one Spark worked on a
token at a time. Now two Sparks run the tensor split: both Sparks work on
every token. You do not set anything. The split needs RDMA between the two
Sparks.

| Two Sparks | v0.1.0 cards | End-of-day cards |
| --- | ---: | ---: |
| Prose, one chat, drafting ON | 38.3 | 53.8 |
| Code, one chat, drafting ON | 65.1 | 100.0 |
| Structured output, one chat, drafting ON | 67.7 | 128.4 |
| Eight chats together, drafting ON | 168.6 | 229.5 |
| First token after a cold 8K prompt, drafting OFF | 2.79 s | 2.19 s |

With drafting OFF, two Sparks write prose at 35.1, against 27.9 in the
v0.1.0 cards.

**One Spark is a little faster.** On one Spark, code went from 76.7 to 80.5
and structured output from 88.7 to 99.9. Prose stayed at 41.7 and 42.0.

**Long prompts start sooner.** On two Sparks, a prompt of 32K tokens or
more now reads in wider passes. With drafting ON, the drafter also reads the
prompt while it waits for the last part (main `285fa8a`). The confirm run
measured that second change: with drafting ON, a 129,220-token prompt gave
its first token in 40.37 s at main `285fa8a`, against 42.09 s on main
`54392da`. With drafting OFF it did not change: 39.73 s against 39.72 s,
the mean of two requests on each main.

## More chats, and longer chats

**More chats at once on two Sparks.** Before main `250fb49`, every chat
reserved the memory for the whole context, even for a short prompt. Now a
chat reserves memory only for the rows it uses. In the capacity test at a
131,072-token context, the test sent 16 short chats (about 1,250 tokens
each), one each second. All 16 were active together, against 2 on main
`54392da`. The first nine chats waited 0.16 s in the queue (median), against
44.8 s on main `54392da`. Two chats of 100,378 tokens, sent 8 s apart, are
still active together.

**Larger context windows.** The context tests measured three windows:

| Setup | Main | Context | Prompt | First token | Writing speed |
| --- | --- | ---: | ---: | ---: | ---: |
| One Spark | `285fa8a` | 131,072 | 120,624 tokens | 66.2 to 66.5 s | 48.3 to 49.7 |
| One Spark | `250fb49` | 262,144 | 201,654 tokens | 120.3 to 120.8 s | 48.4 to 50.0 |
| Two Sparks | `285fa8a` | 262,144 | 201,654 tokens | 68.0 to 68.1 s | 41.2 to 42.7 |

The token IDs were the same in every run of each setup. The default context
stays 32,768 tokens. To get a larger window, start with `--context 131072` or
`--context 262144`.

## The prefix cache

The prefix cache keeps the start of a chat. When the next question starts
the same way, the engine does not read that start again. The cache now
works on two Sparks as well as on one.

In the end-of-day runs, the second question on a 32K-token chat gave its
first token:

| Sparks | Cache on | Cache off |
| ---: | ---: | ---: |
| 1 | 0.63 s | 16.03 s |
| 2 | 0.76 s | 9.95 s |

The first question takes a little longer with the cache on, because the
engine saves the chat: 11.09 s against 10.31 s on two Sparks, and 16.23 s
against 16.04 s on one Spark.

The cache is off by default. To turn it on, see
[turn on the prefix cache](../../INSTALL.md#turn-on-the-prefix-cache).
Turning it on by default is [in progress](#in-progress).

## Use Vade from your own tools

- **The OpenAI-compatible API has a guide.** The
  [API page](../openai-api.md) lists the routes and fields that work, what
  the replies contain and where Vade differs from OpenAI. Host tests replay
  15 client request shapes. Nine of them were captured from the
  openai-python 3.41.0 client.
- **The gateways help more clients.** The core gateway
  (`vade-harness gateway`) answers `/v1/embeddings` with HTTP 501 and a
  reason, instead of 404. It also relays the engine's model list at
  `GET /v1/models`, so Open WebUI, Continue and the OpenAI clients can find
  the model. Both gateways, the core gateway and `vade-gateway`, accept a
  chat history in which the openai-python stream helper sent
  `"role": null`.
- **Setup commands for common clients.** `vade-harness setup claude` prints
  the gateway settings for Claude Code. `setup aider`, `setup continue` and
  `setup open-webui` print the settings for those clients.

## The agent reads PDF files

When the agent reads a PDF file in your project, it now gets the text of
the file, page by page. Each page starts with a `page N of M` line. This
works for text-based PDF files of up to 50 MiB. The agent refuses encrypted
files. A scanned page has no text layer, so the agent gets a note that says
so. You cannot attach a PDF to a chat message yet. The
[harness guide](../../harness/README.md) says what the reader reads and
what it skips.

## The agent reads your project instructions

In direct and agent mode, at the start of a chat, the agent puts your
project's instruction files into its system prompt. Codex and Hermes modes
hand the turn to an external agent, which reads its own files. In each
folder from the git root down to the workspace, the agent reads
`AGENTS.md`, `CLAUDE.md` or `.vade/instructions.md`, the first one it
finds. It also reads `~/.vade/instructions.md` for rules that apply to all
of your projects. It reads at most 32 KiB of one file and marks a file that
it cuts. When a file changes, the agent reads it again
before the next turn. `/instructions` lists the files, and
`--no-instructions` turns them off. See
[project instructions](../../harness/docs/project-instructions.md).

## A long chat rolls over

A long chat with the agent (`vade chat` or `vade-harness agent`) no longer
stops at the end of the context window. When the next turn would not fit,
or at 80% of the window, the model writes one summary of the older turns:
plan, decisions, open tasks, files and facts. The last 2 turns stay word for
word when they fit; when they do not, only the last turn stays. Tool outputs
stay as references to a path and its lines. The chat
shows one line: `[context compacted: kept N turns, summary M tokens]`.
`/compact` does the same on request, and `vade-harness agent --no-compact`
turns the automatic step off. A resumed chat continues from the summary.
[Context and compaction](../context-and-compaction.md) gives the details
and the limits.

## FP8 is a supported route

The FP8 checkpoint is now a supported route, not a legacy one.
`vade up --fp8` starts it on 2, 4 or 6 Sparks. No card has measured six.
In the end-of-day cards, FP8 wrote prose at 36.6 on two Sparks and at 46.7
on four. FP8 is the one model in these cards for which four Sparks write
faster than two. The [FP8 install](../install-fp8.md) gives the steps and
the full cards. Two limits apply to FP8; see [known limits](#known-limits).

## Install and commands

- `sh scripts/install.sh` sets up the Rust tools and the source build on one
  Spark, and prints recovery steps when a step fails.
- A plain-text error starts with `error:` (what happened). When there is a
  next step, a `hint:` line follows. With `--json`, a command that fails
  still answers with its JSON object, and the object holds the failure.
- `vade doctor` runs every check, prints one row for each, and gives the fix
  under each failed row.
- `vade config` names the setup that the other commands will use.
- `--json` works on `doctor`, `config`, `detect`, `version` and `status`.
- `vade status` names the path that your Sparks run and the reason.
- `vade pull` downloads a model from the Hugging Face Hub into
  `~/models/<org>/<name>`. It continues an interrupted download and
  checks the size and hash of each file. `vade launch` and `vade up` check
  those records before they serve an FP4-Local checkpoint. The FP4-Local
  checkpoint is 32 files and 102.26 GB. `vade models` lists the models on
  this machine. For a supported model it gives the command that serves it;
  for another model it gives a recovery step or the reason. See
  [Download models](../pull-models.md).

## In progress

This work was not merged when these notes were written. It is not part of
v0.2.0 until it merges, and these notes will change when it does.

- **The prefix cache on by default.**
- **Reading more document formats.** The agent reads office files (Word,
  Excel and PowerPoint), EPUB, HTML and CSV as text. PDF reading has
  merged; see [the agent reads PDF files](#the-agent-reads-pdf-files).
- **Sessions from the command line.** The agent already lists sessions with
  `/sessions` and resumes one with `/resume`. The new work adds a
  `vade sessions` command and a resume option for `vade chat`.
- **MCP.** The agent uses the tools of MCP servers that you set up.
- **Shell safety.** On macOS, the agent already asks before it runs a
  command that is not on its fixed list of read-only commands. The new work
  adds lists of allowed commands that you keep for a project or for your
  user, and it refuses the most dangerous commands.
- **Structured output, phase 1.** JSON mode for `response_format`.

## Known limits

- **Four Sparks do not make one chat faster.** The four-Spark layer chain
  passes each token through the Sparks in turn. With FP4-Local, four Sparks
  wrote prose at 42.8 in the end-of-day cards, against 42.0 on one Spark and
  53.8 on two. Eight chats together reached 192.9 on four Sparks, against
  177.5 on one and 229.5 on two. Four Sparks read a cold 8K prompt sooner
  than one: 2.18 s, against 3.76 s. We have measured chains of at most four
  Sparks.
- **Text only.** Vade does not read images. An image part in a chat message
  gets HTTP 400.
- **Sampling.** With FP4-Local, greedy decoding is the default, and the
  exactness checks cover only greedy requests. A request that sends any
  sampling field, such as `temperature`, gets the checkpoint's defaults for
  the fields it leaves out. For FP4-Local these are temperature 1, top-k 20
  and top-p 0.95, so the reply is sampled. An explicit `"temperature": 0`
  stays greedy: the engine picks the most likely token. The fields it
  leaves out still come from the checkpoint. FP4-Local's penalties are
  neutral (repetition 1, presence 0, frequency 0), so `"temperature": 0`
  gives the greedy token IDs. Another checkpoint can have penalties that
  change the answer. A sampled request on Flash-Next decodes without
  drafting by default. `min_p` works; `typical_p`, `logit_bias`
  and `best_of` are ignored. See [sampling](../sampling.md).
- **No structured output mode.** The engine ignores `response_format`. Ask
  for JSON in the prompt and check the reply in your code. Phase 1 of
  structured output covers JSON mode only, not JSON schemas.
- **FP8 needs every sampling field for greedy replies.** A request to the
  FP8 server that leaves out a sampling field takes it from the
  checkpoint's sampled settings, even when it sends no sampling field at
  all. Send every sampling field for greedy replies; the
  [FP8 install](../install-fp8.md) gives a full greedy request. The
  gateways add those fields to a request that sends none.
- **FP8 answers depend on the Spark count.** With FP8, each Spark count
  gives the same token IDs on every run for greedy requests. But two Sparks
  and four Sparks matched in only 7 of 66 responses in the end-of-day cards.
  A fix is in screening.
- **No shell tool on Linux.** On the Spark and on other Linux computers, the
  agent reads, searches and edits files, but it does not run commands.

## Upgrade from v0.1.0

**On a Spark, from a source checkout:** the `vade update` of v0.1.0
rebuilds the engine and the agent program, but not the `vade` command
itself. So rebuild the command first. Run these commands from your Vade
checkout:

```sh
vade down
git pull --ff-only
export PATH="$HOME/.cargo/bin:$PATH"
cargo +1.99.0 build --release --offline --locked --manifest-path cli/Cargo.toml
export PATH="$PWD/cli/target/release:$PATH"
./cli/target/release/vade update
vade up
```

`vade update` refuses to run while the local engine runs, so stop the
engine first. It does not download anything. It builds the engine and the
agent program from this checkout and stages them. `VADE_SOURCE` names
another checkout.

**On a Spark, from the launcher bundle:** stop the engine with
`vade down`. Download and unpack the new bundle. Then, in the new bundle
folder, run `./vade update` and `./vade up`. The new bundle has its own
`vade` command. `vade update` checks and stages the files of the bundle.
`VADE_BUNDLE` names another bundle folder.

**From a controller:** run `vade update`. It updates each clean checkout
in your config with `git pull --ff-only`, rebuilds, restages the binaries
and offers a restart. A checkout with local changes stops the update. The
update also rebuilds the controller's own `vade` in `cli/target/release` of
your CLI checkout. The running update and its restart still use the old
program; the new commands work from your next `vade` command.

**Other changes to note:**

- `vade up --fp8` is the new name for `--fp8-legacy`. The old flag still works
  and does the same thing.
- Two FP4-Local Sparks need RDMA. `vade up` refuses `SEQPAR_RDMA=0` for
  them before it contacts a Spark.
- The `VADE_W2_*` settings have no effect any more. The engine chooses the
  path for each number of Sparks and names it in `vade status`.

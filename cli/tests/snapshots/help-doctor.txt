$ vade doctor --help
Check the setup: one line per check, then PASS or FAIL.

Examples:
  vade doctor
  vade doctor --json
  VADE_CONFIG=cluster.conf vade doctor --dry-run

Usage: vade doctor [--json] [--api-key-file PATH] [--dry-run]

Options:
  --json               Print one vade.doctor.v1 object with every check
  --api-key-file PATH  Bearer credential file (or VADE_API_KEY_FILE)
  --dry-run            Show what would happen; change nothing

Notes:
  - On this Spark: config, VADE_HOME writable, ownership, installed binaries,
    model files, nvidia-smi and driver, disk, free memory, port and engine
    health.
  - From a controller: local tools, then SSH, nvidia-smi, disk, free memory and
    model files on each selected Spark, then the fabric and the harness.
  - Also shows the vade binary and version, context, output, drafting and prefix
    cache settings, model JSON files, safetensors count and bytes, and server
    ports on each Spark.
  - Doctor checks the active Sparks, or the default vade up selection, through
    the same SSH options. It does not start an engine or change the setup.
  - Each FAIL row gives the next step. Exit 0 means PASS, 1 means FAIL.
  - One Spark needs no fabric or RDMA; linked Sparks use RDMA by default. Set
    SEQPAR_RDMA=0 for TCP using the configured fabric addresses on any reachable
    interface; QSFP and RDMA memlock are unnecessary in TCP mode.
  - Explicit VADE_CONFIG selects the controller; otherwise generated local setup
    wins. Keep the same VADE_CONFIG and VADE_HOME from start through chat,
    status, logs and down.
